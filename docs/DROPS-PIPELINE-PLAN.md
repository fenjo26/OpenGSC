# Дропы: конвейер вместо набора кнопок — план

План апгрейда `/drops` до уровня, который показывает DropHunter (`drophunter.369whois.online`),
плюс то, чего у него нет. Написан 2026-09-10. Дополняет `DROPS-PLAN.md`, не заменяет его:
воронка, профили реестров и правило корроборации из того документа остаются в силе.

## 0. Что вообще происходит

Метод из постов 369team состоит из двух половин.

**Первая — добыча списка**, руками, вне приложения:
- через биржу ссылок (Miralinks/GoGetLinks): фильтры «в каталоге Google, DR ≥ 25, трафик ≥ 5000»,
  выгрузка площадок консольным скриптом, затем Ahrefs Batch Analysis → Outgoing links → Followed
  → фильтр `Link Type = In Content` → Export;
- через СМИ: Keywords Explorer по локальному ключу («noticias», GEO Spain) → Traffic share by
  domain → берём газету → Site Explorer → Linked domains → фильтры DR 1–35, dofollow,
  linked pages 1–100 → Export.

Обе дороги заканчиваются одним и тем же: **CSV из Ahrefs со списком чужих доменов и их DR**.

**Вторая половина — обработка**, и вот её делает DropHunter: файл + прокси + «Начать» →
список свободных доменов с DR. Всё. Три шага, один экран.

## 1. Кто чего не умеет

DropHunter не умеет ничего, кроме извлечения доменов и проверки свободности. Ни DNS-префильтра,
ни корроборации, ни истории, ни скоринга. Судя по интерфейсу, прокси у него **обязательны** —
без них он просто не запускается.

В `/drops` уже есть всё, чего нет у него: DNS-префильтр (снимает ~90% до платных и лимитируемых
шагов), четырёхзначный разбор ответа whois (`available | registered | refused | empty`), правило
«одного источника мало», профили реестров с троттлингом по зонам, обогащение DR/refdomains/TF,
Wayback, скоринг, группы, watch-цикл.

Не хватает ровно трёх вещей.

## 2. Разрыв 1 — разбор выгрузки Ahrefs (обязательно, иначе метод не работает)

`parseDomainList` берёт **первое поле строки, похожее на домен**, и выбрасывает остальные.
`normaliseDomain` при этом уже умеет полные URL, `www.`, порты, креды и сведение к апексу — то
есть `https://iberconceptos.net/noticias/x` он разберёт правильно.

Проблема в другом. В выгрузке Outgoing links колонка-источник (`Referring page URL`) стоит
**раньше** колонки-цели (`Target URL`). Первое поле, похожее на домен, — это сама газета. То есть
на 143 тыс. строк экспорта из поста текущий импорт даст **один домен**, `elpais.com`, и 143 тыс.
дублей. Метод из постов сейчас физически не проходит через импорт.

Что делать:

- новая функция `parseDomainRows(raw)` рядом с `parseDomainList`, возвращает
  `{ domain, dr?, refdomains?, sourceUrl? }[]`;
- определение колонок по строке заголовка, по списку синонимов: цель —
  `target url | linked domain | domain | referring domain`, рейтинг —
  `domain rating | dr | target dr`, ссылающиеся — `referring domains | ref domains`;
- если заголовок не распознан — падаем на текущее поведение (первое поле, похожее на домен),
  но **говорим об этом в UI**, а не молча;
- ручной переопределитель колонок в интерфейсе: показать распознанные заголовки и дать выбрать
  другие. Экспорты Ahrefs меняются, фиксированный индекс сломается на следующем;
- дедуп по домену с сохранением **максимального** DR среди строк;
- DR из выгрузки пишется сразу в кандидата.

Последний пункт — это не удобство, а деньги. Обогащение через Ahrefs стоит $0.00125 за домен
(этаж в 50 юнитов). Выгрузка на 30 тыс. доменов уже содержит DR — перенос его из файла экономит
около **$37 на каждой такой выгрузке** и снимает целый шаг конвейера.

`parseDomainList` остаётся: он для пасты «просто список доменов».

## 3. Разрыв 2 — пул прокси (главный по объёму работы)

Сейчас проверка идёт с одного IP, троттлинг — по зонам: зоны параллельно, внутри зоны по одному
через `minIntervalMs`. Для `.com` с интервалом в секунды 30 тыс. доменов — это недели.

С пулом единица троттлинга становится парой **(зона, прокси)**: N живых прокси дают почти
N-кратную пропускную способность, не нарушая вежливости к каждому отдельному реестру с точки
зрения одного адреса.

### 3.1. Транспорт — две разные задачи

**RDAP — это HTTPS**, идёт через `safeFetch`. Node 22 отдаёт глобальный `fetch` из undici, но
диспетчер наружу не выставляет. Значит: добавить `undici` в зависимости, `ProxyAgent` для
HTTP-прокси; для SOCKS5 — пакет `socks` плюс свой `Agent` с кастомным `connect`. `safeFetch`
получает необязательную опцию `proxy`.

**Здесь ловушка, из-за которой это нельзя сделать «на коленке».** В `safeFetch` живёт
SSRF-гард: он резолвит цель и запрещает приватные адреса. При работе через прокси мы соединяемся
с прокси, а цель резолвит уже он. Значит гард надо развернуть: проверять адрес **прокси**, а цель
валидировать по имени до отправки. Сделать иначе — либо дыра (прокси на `127.0.0.1` как способ
достучаться до внутренней сети), либо всё перестанет работать.

**WHOIS — это сырой TCP на порт 43**, `net.createConnection` в `whois.ts`. Никакой `fetch` тут ни
при чём. Работают только SOCKS5: `SocksClient.createConnection` из `socks` отдаёт готовый
`net.Socket`, который `whoisQuery` примет как есть, если разнести создание сокета и диалог по
разным функциям. HTTP-прокси годятся, только если разрешают `CONNECT` на 43 — публичные почти
никогда не разрешают. **Это надо написать прямо в интерфейсе:** «для WHOIS нужны SOCKS5,
HTTP-прокси покроют только RDAP».

### 3.2. Хранение и жизненный цикл

- модель `DropProxy` в схеме: `url`, `kind` (`http | socks5`), `lastOkAt`, `lastCheckedAt`,
  `failures`, `avgMs`, `enabled`. Все поля строками/числами — схема идёт через `db push`,
  миграции в этом репозитории не пишутся;
- валидатор: не «соединился», а **вернул ожидаемый ответ** от известного RDAP-эндпоинта с
  коротким таймаутом. Прокси, который принимает соединение и отдаёт заглушку, хуже мёртвого;
- прогресс валидации как у них — `2930/4604 проверено · валидных: 26`. Цифра 0.9% на их же
  скриншоте не случайна: публичные списки почти целиком мёртвые, и пул придётся чистить
  постоянно, а не один раз;
- ротация: least-recently-used среди живых; выбывание после K подряд ошибок; возврат в строй по
  таймеру, а не навсегда;
- прокси у нас **не обязательны**, в отличие от DropHunter. Без них всё работает как сейчас,
  просто медленно. Обязательным шагом это делать нечестно.

### 3.3. Что не меняется

Отказ реестра по-прежнему не вердикт: строка остаётся на месте и возвращается по бэкоффу.
Корроборация тоже остаётся — с прокси она становится вдвое дороже по запросам, но отменять её
нельзя: в исходном посте 43 «свободных» из 487 оказались ложными именно из-за одного источника.

## 4. Разрыв 3 — интерфейс, который объясняет себя

Сейчас страница — плоский набор кнопок, и по ней невозможно понять ни порядок, ни смысл.
Нужен видимый конвейер с состоянием каждого шага.

- **Шаг 0 «Откуда взять список».** Свёрнутый блок с двумя рецептами из раздела 0, по пунктам,
  с названиями фильтров Ahrefs. Без него пользователь не знает, что вставлять, — и это, судя по
  постам, и есть главный барьер, а не сама проверка.
- **Шаг 1 «Файл».** Дропзона (сейчас только textarea) + показ распознанных колонок с
  возможностью переопределить + предпросмотр: сколько доменов, сколько из них с DR, сколько
  отбраковано и по каким причинам. Сводка отбраковки уже есть, остальное нет.
- **Шаг 2 «Прокси».** Textarea, кнопка «Проверить», прогресс, «валидных N». Помечен как
  необязательный, с одной строкой о том, что он ускоряет и почему для WHOIS нужен SOCKS5.
- **Шаг 3 «Запуск».** Одна кнопка вместо трёх: DNS → реестры → (опционально) DR/Wayback, с
  прогрессом по стадиям и текущей стадией. Отдельные кнопки остаются для тех, кто хочет
  прогнать один шаг.
- **Шаг 4 «Результат».** Свободные с DR, кнопка экспорта CSV.
- Короткие плашки «почему так»: почему DNS идёт первым (снимает ~90% до лимитируемых запросов),
  почему «свободно» без корроборации не красится зелёным, почему `.gr` уходит в отдельную стадию.

## 5. Чего этот конвейер НЕ чинит

`.gr`. Прокси не помогают, когда спрашивать некого: у зоны нет ни RDAP, ни живого публичного
WHOIS. И для греческих СМИ большая часть исходящих ссылок — как раз `.gr`, то есть на основном
ГЕО этот конвейер даст заметно меньше, чем на испанском примере из поста. Ответ по `.gr` остаётся
прежним: API регистратора, отдельной задачей.

Конвейер имеет смысл для gTLD (`.com/.net/.org`) и для зон с живыми реестрами — а их в выгрузках
испанских, немецких и итальянских СМИ большинство.

## 6. Риски, которые надо назвать вслух

- **Публичные прокси**: 0.9% выживаемости. Пул — расходник.
- **Массовые запросы к реестрам** через прокси противоречат AUP большинства из них. Со своего IP
  цена ошибки — бан своего IP; через прокси — просто перестанет работать. Вежливые дефолты не
  выкручиваем, интервалы по зонам оставляем.
- **Скрипт выгрузки с биржи** (`getlinks.js` из поста) — чужой код в консоли залогиненного
  аккаунта. В приложение он не переезжает и в документации не воспроизводится: приложение
  начинает работу с готового CSV.

## 7. Порядок

| | Что | Размер | Зачем именно в этом порядке |
|---|---|---|---|
| A | Разбор выгрузки Ahrefs + перенос DR | малый | Без него метод из постов не проходит вообще: импорт схлопывает выгрузку в один домен |
| B | Пул прокси (модель, валидатор, транспорт RDAP+WHOIS) | большой | Снимает потолок скорости; всё остальное после него имеет смысл на объёме |
| C | Конвейер и объяснения в UI | средний | Осмысленно, когда A и B есть — иначе объяснять нечего |
| D | Экспорт результата в CSV | малый | Закрывает круг: выгрузка → проверка → выгрузка |

A даёт пользу сам по себе и не зависит от B. Начинать с него.
