# Uptime Monitor

Аптайм-монитор отвечает на вопрос, который Search Console закрывает слишком поздно: «упал ли
сайт прямо сейчас». Точка статуса у каждого сайта на дашборде, упавшие сайты поднимаются в
группу «Требуют внимания», алерт в Telegram/Slack при падении и при восстановлении, история
инцидентов на вкладке Health.

**Стоимость: бесплатно — работает на вашем сервере.** Никаких внешних платных сервисов:
проверка — один HTTP GET из вашего инстанса к вашему сайту.

## Что проверяется

- **URL** — по умолчанию корень сайта (`sc-domain:example.com` → `https://example.com/`). Можно
  поменять на любую страницу (в т.ч. «живьевой» эндпоинт вроде `/health`).
- **HTTP-код** должен попадать в «допустимые» (по умолчанию `200-399`; формат — диапазоны и
  отдельные коды через запятую).
- **Ключевое слово** (необязательно): страница должна содержать этот текст — ловит «сайт
  отвечает 200, но отдаёт пустой шаблон».
- **Латентность** — от начала запроса до конца чтения тела (safeFetch буферизирует тело целиком
  до resolve, разделения «заголовки получены» он не даёт). Ключевое слово ищется в теле, так что
  тело читается всегда; «медленно» честно означает «медленно для пользователя». Ответ до 2 МБ.
- User-Agent — `OpenGSC-Uptime/1.0 (+https://opengsc.org)`, редиректы — до 5, таймаут — настроечный.

## Когда считается «упал»

Не первая же ошибка: статус меняется на `down` после **N неудач подряд** (по умолчанию 2,
настраивается). Первая неудача мониторинга в статусе `up` планирует быструю повторную проверку
через 30 секунд — короткий сетевой чих не открывает инцидент.

Инцидент начинается с **первой** неудачной проверки серии (а не с подтверждающей) — иначе
длительность простоя занижалась бы на интервал. Если серия прервалась успехом до порога,
инцидент удаляется: «1 неудача, потом успех» — не инцидент.

**Только переход — событие.** Сайт, который уже лежал в момент включения мониторинга, алерт
«упал» не присылает: вы и так знаете. Алерты — только на переход `up → down` и один раз на
инцидент (`AlertEvent.dedupeKey`). «Поднялся» приходит с длительностью простоя. Пока сайт
лежит — напоминания каждые N часов (0 = выкл). Отдельный переключатель «алертить и о медленных»
(degraded) — по умолчанию выкл.

## Почему нет алерта при сбое сети сервера

Если за один проход разом «упали» почти все сайты с сетевыми причинами (timeout/DNS/connect),
падение — у **самого сервера**, а не у сайтов: ≥ 3 мониторов проверено и ≥ 80% упали по сети →
статус всех мониторов становится «проверка недоступна (сеть сервера)», точки серые, состояние
не меняется, инциденты не открываются, алертов нет. Результаты пишутся в историю проверок как
есть. HTTP-ошибки (например, 500) под это правило не попадают — это проблема сайтов, не сети.

Важно: серые проверки в этот период всё же записываются в историю, поэтому «аптайм 24 ч» в
подсказке точки может просесть после сбоя сети самого сервера — это честно отражает то, что
проверок не было. Долгосрочные проценты (7/30/90 дней, из дневных агрегатов) сбой одного
прохода не портит.

## Heartbeat — «кто сообщит, что упал сам сервер»

Настройки → Мониторинг аптайма → Heartbeat URL. Если задан, OpenGSC пингует его не чаще раза в
минуту. Внешний сервис (healthchecks.io, UptimeRobot heartbeat, Better Stack) поднимет тревогу,
когда пинги перестанут приходить — то есть когда умрёт ваш VPS, контейнер или процесс. Это
дёшево и покрывает единственный случай, который монитор не может проверить сам.

## Cloudflare и 403

Некоторые WAF/CDN режут неизвестных User-Agent'ов — проверка приходит с честным 403, и сайт
выглядит упавшим, хотя он работает. Лечится добавлением кода в «допустимые» на вкладке Health:
`200-399,403`. То же для 401 (basic auth) и других ожидаемых кодов.

## Данные и ретеншн

- **Сырые проверки** (`UptimeCheck`) — 7 дней, потом удаляются суточной уборкой.
- **Дневные агрегаты** (`UptimeDaily`) — навсегда: проверки, неудачи, сумма/максимум латентности
  (по успешным), время простоя по дням.
- **Инциденты** (`UptimeIncident`) — начало, конец, причина; длительность считается от первой
  неудачи серии.
- Автозапись: монитор создаётся каждому живому (не архивному, не скрытому) сайту воркспейса с
  включённой опцией (по умолчанию включена), первые проверки раскиданы случайно внутри
  интервала.

## API и MCP

- `GET /api/uptime/status` — бейджи всех сайтов (дашборд, раз в 60 с).
- `GET·PUT /api/uptime/[siteId]` — сводка и настройки монитора; смена URL сбрасывает статус и
  проверяет сразу.
- `POST /api/uptime/[siteId]/check` — «проверить сейчас».
- `GET·PUT /api/uptime/settings` — настройки воркспейса.
- MCP: `get_uptime` — статусы всех сайтов или сводка одного (`site`).
