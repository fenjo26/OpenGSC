**Почему планировщика пока нет.** Фоновый тик, который сам ходит по публичным
RDAP-нодам, — это то, чем зарабатывают бан, если бэкофф ошибётся. Разведка фазы 0 ответила
на вопросы по поведению зон (см. 4a): `.gr` не проверяем вовсе, `.fr` предсказуем, Verisign
RDAP 429-ит вспышками даже на единичных запросах. Кнопка по-прежнему честнее тика: она
работает, только когда человек смотрит на результат. Планировщик ставить после первого
реального прогона на большом списке и на VPS, где IP не делится с сотнями чужих запросов.

**Проверить DNS-предфильтр отсюда нельзя** — ни у контейнера, ни у шелла на маке нет
сети. Оттестирована чистая часть: классификация кодов ошибок резолвера и то, что
`unknown` отправляет кандидата дальше, а не отсеивает. Сам резолв проверится на VPS.

**Прежде чем запускать приложение — `npx prisma db push`.** Клиент Prisma в этом
чекауте сгенерирован до новых моделей. Модели читаются через `prisma as any`, как уже
сделано в 44 местах репозитория (`siteScan`, `seoJob`, `geoAudit` и другие), поэтому
`tsc` чист. А роуты ловят «нет таблицы» и отдают `notMigrated: true` — страница
показывает подсказку вместо 500.

Ни `prisma validate`, ни `generate` в этой среде выполнить нельзя: `binaries.prisma.sh`
отдаёт 403 и с мака, и из контейнера. Значит синтаксис моделей проверен только глазами
и подтвердится при первом `db push`.

## 1. Почему это отдельный модуль, а не вкладка сайта

Всё в `/site/[id]` привязано к `Site` — домену, который пользователь уже держит.
Дроп — это домен, которого у него нет и, скорее всего, не будет: из 50 000 кандидатов
покупаются шесть. Кандидат живёт в своей таблице, со своим жизненным циклом, и только
после покупки может стать `Site`.

Ближайший структурный аналог в репозитории — `/indexer`: свой раздел, свои таблицы
(`IndexerDomain`, `IndexerQueue`, `IndexerLog`), свой лэйаут с подстраницами. Модуль
дропов копирует эту форму.

## 2. Воронка

Один кандидат проходит фиксированную последовательность. Каждая ступень дешевле
следующей и существует затем, чтобы до следующей дошло как можно меньше строк.

```
ingest          импорт: CSV, Ahrefs, краулер, зонные диффы
   |
dns_prefilter   резолв NS/A. Есть записи -> домен занят, выбывает. БЕСПЛАТНО, убивает ~90%
   |
availability    RDAP -> whois. 404 от RDAP сам по себе ничего не значит
   |
confirmed       подтверждение через API регистратора перед покупкой
   |
enrich          Ahrefs: DR, refdomains, анкоры, is_lost
   |
history         Wayback CDX: снимки, период между смертью и сейчас
   |
scored          один балл, по которому сортируется таблица
   |
watch / buy     алерт в Telegram, дальше руками (v1) или через API регистратора (v2)
```

**Порядок ступеней — это и есть весь смысл модуля.** Любой из девяти публичных
репозиториев, которые смотрели, начинает сразу с RDAP по списку из UI. На 50 000 строк
это 50 000 запросов к публичным RDAP-нодам, бан и трое суток ожидания. DNS-предфильтр
первым шагом стоит ноль и оставляет от списка десятую часть.

## 3. Откуда берутся списки

Вопрос «откуда тот чувак взял 50 021 домен» имеет скучный ответ: это дневной объём
удалений в `.com`. Способы получить его, от бесплатного к платному:

**Зонные файлы ICANN CZDS (бесплатно, регистрация с обоснованием).**
Скачиваешь зону `.com` сегодня и вчера, диффишь. Имена, которые вчера были, а сегодня
нет, — удалённые за сутки домены. Это авторитетный источник, не чей-то парсинг.
Зона `.com` — порядка 160 млн строк, ~2-3 ГБ в gzip; диффить надо на VPS через
`sort`/`comm`, не в ноде и не в памяти. Заявка на доступ рассматривается неделями,
подавать стоит сразу.

**expireddomains.net** — 676 зон, обновление ежедневно, но **API нет**, только
веб-интерфейс. Это ровно тот случай, для которого у тебя есть ZennoPoster.

**Ahrefs, `site-explorer/refdomains` донора.** Берём крупный сайт в нужной тематике,
вытягиваем его ссылающиеся домены, гоним через воронку. Клиент уже написан
(`src/lib/seo/metrics.ts`), стоимость — см. раздел 7.

**Ahrefs, битые исходящие донора.** Классический источник «дропа с живым ссылочным»:
если с крупного новостника стоит ссылка на домен, который отдаёт 404, домен, скорее
всего, мёртв, а ссылка — жива.

**Собственный краулер.** `/crawler` и так обходит чужие сайты и видит их исходящие
ссылки. Каждая внешняя ссылка на неразрешающийся хост — бесплатный кандидат.

**Платные фиды** (WhoisFreaks и подобные) — ежедневные списки dropped/pending-delete
по 1500+ зон. Имеет смысл, только если CZDS не дали.

**Реестровая открытка по .fr.** AFNIC публикует открытые данные по зоне `.fr`,
включая ежедневные списки. Если формат содержит удаления — это лучший из возможных
источников по этой зоне, потому что он от самого реестра. Проверить в фазе 0.

## 4. Реестровые профили — как закрываются .gr и .fr

Ключевая абстракция. Ни один из просмотренных репозиториев её не имеет: у них
захардкожена карта `TLD -> URL` и общий набор регулярок, и на любой нестандартной зоне
всё разваливается молча.

```ts
// src/lib/drops/registries.ts
export interface RegistryProfile {
  tld: string;
  /** RDAP-эндпоинт. Отсутствует — значит зона идёт сразу в whois. */
  rdap?: string;
  /** Хост whois. Отсутствует — определяется через whois.iana.org и кэшируется. */
  whoisHost?: string;
  /** Доп. паттерны "свободен" сверх общего набора. Реестры формулируют по-разному. */
  availablePatterns?: RegExp[];
  /** Минимальный интервал между запросами К ЭТОМУ реестру, мс. */
  minIntervalMs: number;
  /** Требует подтверждения через API регистратора: реестр не отдаёт надёжного ответа. */
  needsRegistrarConfirm?: boolean;
  notes?: string;
}
```

Профили на старт:

| Зона | RDAP | Комментарий |
|---|---|---|
| com, net | `rdap.verisign.com/{tld}/v1/domain/` | Эталон, всё предсказуемо; RDAP мигрённо 429-ит даже на 1 зап/2с — см. результаты фазы 0 |
| org | `rdap.publicinterestregistry.net/rdap/domain/` | |
| io, me, sh, ac | `rdap.identitydigital.services/rdap/` | |
| de | `rdap.denic.de/` | whois отдаёт `%% no entries found`; подтверждено живьём |
| xyz | `rdap.centralnic.com/xyz/` | подтверждено живьём; rdap.org зону не маршрутизирует и сам 403-ит вспышками |
| **fr** | `rdap.nic.fr/` | **Подтверждено фазой 0.** Свободен = `%% NOT FOUND`, свой паттерн в профиле |
| **eu** | нет и не будет | **Подтверждено фазой 0.** whois.eu, свободен = `Status: AVAILABLE`; свободные вердикты навсегда некорроборированы |
| **gr** | нет; WHOIS тоже не работает | **Подтверждено фазой 0.** Порт 43 у реестра «тёмен» (принимает TCP и молчит), IANA не публикует хост. Только API регистратора, см. профиль |
| прочее | `rdap.org/domain/` (бутстрап) | Фолбэк; капризен (403 вспышками), для крупных зон явный эндпоинт лучше |

`.gr` — закрытая зона. Нет публичного RDAP, порт 43 принимает соединения и никогда не
отвечает, `whois.ics.forth.gr` больше не резолвится, в ответе IANA строка `whois:` пустая.
Единственный надёжный путь — API регистратора, который в этой зоне работает. До фазы 6
каждая `.gr`-проверка честно падает в `no_usable_source` с бэкоффом: это дорого-занятно
ровно один раз, после чего список `.gr` — не массовый прогон, а наблюдение через регистратора.

## 4a. Результаты фазы 0 (разведка, 2026-09-07, с мак-шелла с сетью)

Что проверено и что из этого следует (всё уже внесено в `registries.ts`/`patterns.ts`/`ingest.ts`):

1. **IANA-бутстрап: `.fr` есть, `.gr`/`.eu`/`.de`/`.io`/`.me` — нет.** Отсутствие в бутстрапе
   ≠ отсутствие RDAP: у `.de` и `.io` свои эндпоинты работают. Но `rdap.org` при этом зону
   не маршрутизирует (404 без редиректа) — для таких зон явный эндпоинт в профиле обязателен,
   иначе зона никогда не получает корроборации.
2. **`rdap.nic.fr` живой** (404 свободный / 200 занятый, ~0.3с). Формулировка свободного
   WHOIS: `%% NOT FOUND` — общий якорь `^not found` мимо, паттерн `/^%+\s*not found/` в профиле.
3. **`rdap.centralnic.com/xyz/` живой** (404/200). Добавлен профиль `.xyz`: rdap.org не
   маршрутизирует зону и сам по себе 403-ит вспышками — бутстрап как постоянный путь ненадёжен.
4. **`.gr` непроверяем без регистратора** (см. выше). `gr.whois-servers.net` ведёт на RIPE,
   чьё «not found» ничего не доказывает — ещё один повод не верить фолбэкам.
5. **`.eu`: RDAP нет вообще** (в бутстрапе отсутствует, `rdap.eu` не отвечает),
   `whois.eu` свободен = `Status: AVAILABLE` — общий паттерн ловит. Юридическая простыня
   над статусом парсится как свидетельство регистрации; решает строка статуса.
6. **Verisign RDAP 429-ит вспышками при копеечной нагрузке** (1 запрос / 2с: серия 404,
   серия 429, снова 404 — за минуты, с одного IP). При этом WHOIS Verisign отвечал чисто
   всё время. Следствие в коде: RDAP 429 больше не хоронит строку сразу — спрашивается WHOIS,
   и только его отказ пишет `rate_limited`.
7. **Баг парсера, пойманный живьём:** штамповка «TERMS OF USE: You are not authorized to
   access or query our Whois database…» идёт в **каждом** ответе Verisign — и неанкоренный
   рефьюзал-регулярник читал каждый нормальный ответ .com/.net как «отказ», уронив всю зону
   в `rate_limited`. Группа «denied» теперь якорится к началу строки.
8. **Баг класса «свободен на занятом», пойманный живьём:** реестры отвечают «no match» на
   **хост-образные** имена — `www.google.com` даёт RDAP 404 + WHOIS «No match» =
   корроборированное «свободен» на домене Google. `ingest.ts` теперь сводит каждую строку
   к регистрируемому апексу (`apexOf`: суффикс + 1 лейбл), `www.`-префиксы и прочие хосты
   схлопываются в апекс. Прежний тест «www не отрезаем» заменён: аргумент «список субдоменов
   не должен схлопываться» проигрывает аргументу «хост-строка даёт ложное свободно», потому
   что ложное «свободен» — тот класс ошибок, ради которого модуль и писан.

Контрольный прогон после фиксов (`scripts/drops-check.ts`): `.io`, `.de`, `.fr`, `.xyz`,
`.com`, `.net` — свободные имена `AVAILABLE ✔✔` (RDAP 404 + WHOIS согласны); `afnic.fr`,
`denic.de`, `github.com` — занятые распознаны; `.gr` — честный `no_usable_source`; строка
`192.0.2.1` отбракована на ingest; `https://www.Google.com/` → `google.com` → `dns:delegated`.

## 5. Контракт: модели

**Поправка к тому, что я писал раньше.** Правится **только** `prisma/schema.prisma`.
`schema.mysql.prisma` генерируется из него в `prisma.config.ts` и помечен «GENERATED —
do not edit»; папка `prisma/migrations/` в развёртывании не участвует. Схему накатывает
`prisma db push` — из `docker-entrypoint.sh`, из `update.sh` и из инструкций README.
Значит писать миграцию руками не нужно вообще.

Два ограничения схемы, которые легко нарушить:

- **типа `Json` в этом проекте нет.** Prisma не поддерживает его на SQLite, и весь JSON
  здесь лежит в `String` с комментарием `// JSON: ...` (`DemandSearch.rows`,
  `TrafficCache.payload`). `topAnchors` — тоже `String?`.
- **строка в составном ключе — это `VARCHAR(191)` на MySQL.** Длиннее — ошибка на
  записи и только на MySQL. Поэтому `ingest.ts` режет домены по 191 символу, а не по
  253 из спецификации DNS.

```prisma
/// Один прогон: импорт списка или выгрузка донора. Даёт группировку в UI ("Запуск").
model DropRun {
  id        String   @id @default(cuid())
  userId    String
  label     String?
  source    String   // csv | ahrefs_refdomains | ahrefs_broken | crawler | zone_diff
  sourceRef String?  // домен донора / имя файла / дата зоны
  total     Int      @default(0)
  createdAt DateTime @default(now())
  finishedAt DateTime?
  candidates DropCandidate[]
  @@index([userId, createdAt])
}

/// Кандидат. Уникален глобально по (userId, domain): один и тот же домен может прийти
/// из трёх источников, и три строки на него — это три независимых проверки одного
/// и того же у трёх реестров. Связь с прогонами — через runId последнего появления.
model DropCandidate {
  id       String  @id @default(cuid())
  userId   String
  runId    String?
  domain   String
  tld      String

  // ── воронка ──────────────────────────────────────────────────────────────
  stage    String  @default("ingested")
  // ingested | dns_checked | resolved_taken | checking | available | taken
  // | confirmed | rejected | acquired
  dnsHasRecords Boolean?
  lastStatus    String?  // registered | available | rate_limited | error
  lastHttp      Int?
  lastError     String?
  consecutiveErrors Int  @default(0)
  nextCheckAt   DateTime?
  lastCheckedAt DateTime?
  checkIntervalMin Int   @default(1440)
  registryExpiresAt DateTime?
  registryStatus String? // "pendingDelete", "redemptionPeriod" из RDAP, через запятую

  // ── обогащение ───────────────────────────────────────────────────────────
  dr           Float?
  refdomains   Int?
  refdomainsDofollow Int?
  liveBacklinks Int?
  topAnchors   String?  // JSON: { anchor: string, count: number }[]
  metricsAt    DateTime?

  // ── история ──────────────────────────────────────────────────────────────
  waybackSnapshots Int?
  waybackFirstAt   DateTime?
  waybackLastAt    DateTime?
  waybackGapDays   Int?      // сколько домен мёртв
  historyVerdict   String?   // clean | topic_shift | spam_period | unknown
  historyNote      String?   // человекочитаемо, заполняется AI-проходом
  historyAt        DateTime?

  score     Float?
  starred   Boolean  @default(false)
  note      String?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  run    DropRun? @relation(fields: [runId], references: [id], onDelete: SetNull)
  events DropEvent[]

  @@unique([userId, domain])
  @@index([userId, stage, score])
  @@index([nextCheckAt])
}

/// Append-only. Без него невозможно объяснить, почему домен вчера был "свободен",
/// а сегодня "занят", и какой именно ответ реестра к этому привёл.
model DropEvent {
  id          String   @id @default(cuid())
  candidateId String
  type        String   // info | available | taken | rate_limited | error | bought
  message     String
  createdAt   DateTime @default(now())
  candidate   DropCandidate @relation(fields: [candidateId], references: [id], onDelete: Cascade)
  @@index([candidateId, createdAt])
}
```

## 6a. Два трека проверки: A-Parser и встроенный

Уточнение, меняющее фазу 1. Оказалось, что у A-Parser есть парсер **`Net::Whois`**,
который делает ровно то, ради чего планировался порт 400 строк из
`BigDesigner/project-backorder`: сам выбирает RDAP или WHOIS **по зоне домена**, с
приоритетом RDAP, падает на проверку DNS, когда ни то ни другое не отвечает, понимает
IDN и отдаёт готовые поля — `$registered`, `$expire_date`, `$creation_date`, `$ns`,
`$registrar`, статусы домена. Плюс к этому — то, чего у нас нет и не будет: пул прокси
и многопоточность.

Поэтому треков два, и выбирается трек по наличию соединения.

### Трек A — A-Parser (массовый прогон)

Цепочка ровно та, которую советуют на форуме самого A-Parser для поиска брошенных
доменов: **список -> фильтр по коду ответа -> `Net::DNS` -> `Net::Whois`**. То есть
наша воронка из раздела 2, только первые три ступени исполняет чужой движок со своими
прокси.

Транспорт **уже написан**: в `src/lib/seo/aparser.ts` есть `aparserAddTask`,
`aparserTaskState`, `aparserTaskResults` — асинхронный task API. Для 50 000 доменов
нужен именно он, а не `oneRequest`: тот блокирует до конца парса и упрётся в
`APARSER_DEFAULT_TIMEOUT_MS` (120 с) на первой же тысяче.

Что дописать:

1. В `src/lib/seo/aparserCatalog.ts` добавить в `APARSER_CAPABILITIES` две записи —
   `Net::Whois` и `Net::DNS`, ключи локалей `aparserCapWhois` / `aparserCapDns`.
   `availableParsers` из `info` остаётся авторитетом: нет парсера в списке — трек A
   в UI выключен, а не «попробуем и упадём».
2. `src/lib/drops/aparserAvailability.ts` — сборка задачи, поллинг `taskState`,
   разбор результата в `AvailabilityResult`. Файл отдельный, на общем клиенте, а не
   рядом с ним: та же логика, из-за которой `geoAparser.ts` лежит отдельно от
   `aparser.ts`.
3. Отображение полей A-Parser в нашу воронку:
   `$registered = false` -> `available`; `$ns` непустой -> домен занят независимо от
   того, что сказал whois (это и есть корроборация из раздела 6, только бесплатная);
   `$expire_date` -> `registryExpiresAt`; статусы -> `registryStatus`.

Настройки парса не выдумывать. Модератор A-Parser на прямой вопрос про массовую
проверку доменов отвечает: **запускать на дефолтных настройках парсера и не ставить
«No Proxy»**. `Some error` в логе там — это обрыв соединения, а не отказ реестра;
задача сама рестартует. Соответственно наш поллер не должен считать такие строки
за `error` и накручивать `consecutiveErrors`.

### Трек B — встроенный (наблюдение и фолбэк)

Остаётся нужным, потому что A-Parser в этом приложении опционален: пункт меню
появляется, только когда сохранено соединение. Без него модуль обязан работать —
медленнее и на меньших объёмах, но работать.

Здесь и живёт порт из `project-backorder`: `registries.ts`, `patterns.ts`,
`availability.ts`, `dns.ts`. Область применения — списки наблюдения на сотни, а не
десятки тысяч доменов, суточный интервал, ускорение до 15 минут на `pendingDelete`.
Для `.gr`, где массового прогона может не быть в принципе, трек B — основной.

### Что это меняет в фазах

Фаза 1 раздваивается. **1a** — трек A: короче, даёт результат сразу и на реальном
объёме. **1b** — трек B: порт RDAP/whois, нужен для зон, где A-Parser не помогает,
и для инсталляций без него. Начинать с 1a.

## 7. Деньги

Ahrefs через GroupBuySEO: `units = max(50, поля x строк)`, $0.000025/юнит,
неудачные и закэшированные ответы стоят 0. Подробности — `docs/METRICS.md` и заметка
по шлюзу.

Домен поштучно упирается в 50-юнитный пол: **$0.00125 за домен**. То есть:

| Объём | Стоимость обогащения |
|---|---|
| 1 000 доменов | ~$1.25 |
| 10 000 | ~$12.5 |
| 50 000 | ~$62 |

Это на порядок дешевле, чем кажется, но обогащать надо **после** воронки, а не до:
DNS-предфильтр и проверка свободности бесплатны, и после них из 50 000 остаётся
1-2 тысячи. Реальный счёт — доллар-два за прогон.

Что нельзя добавлять в выгрузку кандидатов: `traffic` (10 юнитов), `traffic_domain`
(10), `refdomains_source` (5). У мёртвого домена трафик по определению ноль — поле
утраивает счёт и не меняет ни одного решения.

Wayback CDX — бесплатно и без ключа.
DNS, RDAP, whois — бесплатно, лимит только по частоте.

AI-проход по истории (та самая кнопка «Пересчитать данные + AI») тратит кредиты
пользователя, поэтому подчиняется общему правилу репозитория: отдельная кнопка,
подтверждение перед запуском, асинхронная джоба с поллингом. Ставится в фазе 4 и
только на отобранные вручную строки, не на весь список.

## 9. Что осознанно не делаем в v1

- **Не ловим pending delete в секунду освобождения.** Домены в pending delete уходят
  дропкатчерам с сотнями подключений к реестру; конкурировать с ними из одного
  Next-процесса бессмысленно. Модуль ищет то, что уже свободно и никому не понадобилось.
  Для интересных pending-delete имён — сторонние сервисы бэкордера.
- **Не строим свой whois-прокси-пул.** Если зона лимитирует — снижаем частоту и
  сокращаем список, а не размазываем нарушение по прокси.
- **Не покупаем автоматически.** См. фазу 6.

## 10a. Отдельная задача: A-Parser не виден в меню

Не про дропы, но найдено по дороге и уже починено.

A-Parser настраивается тремя способами, и сервер разбирает их в таком порядке
(`resolveBaseUrl` / `envPassword`): переменные окружения `OPENGSC_APARSER_BASE_URL`
и `OPENGSC_APARSER_PASSWORD` — они **побеждают всё остальное**; затем серверное
зеркало настроек владельца (`User.seoSettings`); и только потом `localStorage`.

При этом **обе** клиентские проверки смотрели только в `localStorage` — и пункт меню
в `DashboardShell.tsx`, и сама страница `/aparser`, которая на том же условии писала
«не настроено». То есть развёртывание, которое документация модуля прямо рекомендует
(«Docker deployments should set the env var»), оказывалось ровно тем, где A-Parser
работает, но недоступен из меню. Тот же симптом у любого, кто настроил его в другом
браузере.

Починка: `GET /api/aparser` с тем же owner-only guard, что и POST, отдаёт
`{ configured, fromEnv }` и больше ничего — ни URL, ни пароля. Клиентский хелпер
`src/lib/seo/aparserConfigured.ts` сначала отвечает синхронно из `localStorage`
(чтобы не мигало), и только если там пусто — спрашивает сервер, кэшируя ответ на
время жизни страницы, чтобы меню и страница не спрашивали дважды.

## 10. Отдельная задача: адаптивная навигация

Не относится к дропам, но чинить надо до фазы 5, иначе десятый пункт в баре добьёт то,
что и сейчас не помещается.

### Что сломано

`NavLinks` в `src/components/DashboardShell.tsx` рисует девять-десять кнопок в
`<nav style={{ display: "flex" }}>` инлайновыми стилями. Инлайновый стиль не может
содержать медиазапрос, поэтому на ширине телефона бар просто вылезает за экран.
Во всём `src/` медиазапросы есть **только** в `globals.css` (три штуки, строки 643-668),
и все три про сетки внутри страниц, не про шапку.

Шапка `TopBar` вдобавок жёстко задаёт `height: 48px` и `padding: 0 24px`.

### Как чинить

**Свап делать через CSS, а не через `window.innerWidth` в React.** Замер ширины в
компоненте даёт разный HTML на сервере и на клиенте, то есть hydration mismatch и
прыгающую шапку при загрузке. Правильный путь: обе версии всегда в DOM, видимость
переключает медиазапрос.

В `globals.css`, рядом с существующим блоком `@media (max-width: 900px)`:

```css
/* ── Шапка: горизонтальный бар на десктопе, бургер на телефоне ───────────── */
.nav-desktop { display: flex; align-items: center; gap: 4px; margin-left: 20px; flex: 1; }
.nav-burger  { display: none; }

@media (max-width: 900px) {
  .nav-desktop { display: none; }
  .nav-burger  { display: flex; margin-left: auto; }
  .topbar      { padding: 0 12px; }
}

.nav-sheet {
  position: absolute; top: 48px; left: 0; right: 0;
  background: var(--color-card);
  border-bottom: 1px solid var(--color-border);
  box-shadow: 0 8px 32px rgba(0,0,0,0.35);
  display: flex; flex-direction: column; padding: 6px 0; z-index: 45;
}
```

В `DashboardShell.tsx`:

1. Массив `items` вынести из `NavLinks` в функцию `useNavItems()` — его теперь читают
   двое, и дублировать список из десяти пунктов между баром и панелью нельзя.
2. `<nav style={{...}}>` -> `<nav className="nav-desktop">`, инлайновые стили самих
   кнопок оставить как есть.
3. Рядом — кнопка-бургер (`Menu` из `lucide-react`, он уже в зависимостях) с
   `className="nav-burger"`, по клику раскрывает `.nav-sheet` с теми же пунктами
   в столбик.
4. Закрытие: клик по пункту, клик по подложке (`position: fixed; inset: 0`) и смена
   `pathname` — последнее через `useEffect` на `pathname`, иначе панель остаётся
   открытой после перехода.
5. `aria-label` и `aria-expanded` на кнопке.
6. `<header>` получает `className="topbar"` к существующим инлайновым стилям.

### Проверка

Прогнать на 375 (iPhone SE), 768 (планшет портрет) и 1440. Смотреть три вещи: бар не
создаёт горизонтальный скролл; открытая панель не уезжает под контент (`z-index` шапки
40, панели 45, меню аватара 50 — не пересекать); переход по пункту закрывает панель.

Ключи локалей новые не нужны — панель показывает те же `t(...)`, что и бар.

## 11. Бэклог идей из референсов (не v1)

Источники: пост-оригинал «Доделал поиск дропов» (скрин каталога — референс UI, см. раздел 8 фаза 5)
и отчёт «DROP//DOMAIN OPS» 09.2026 (турнирный ресёрч: каскады скрининга 100k→500, ярусы цен,
скор-карта buy/pass, консенсусные пороги практиков). Оба сходятся с нашей воронкой в главном —
бесплатные сигналы всему потоку, платные только выжившим; сюда попадает то, что мы сознательно
не кладём в волну P0–P1.5.

**Скор-карта с вето (score.ts v2).** Сейчас скор аддитивный. Правильнее решение двухступенчатое:
auto-veto до всякого скоринга — блок-листы/санкции, gap-301 на спам (canonical-след в CDX),
смена тематики (historyVerdict = topic_shift — поле уже есть), >2 дропов в истории, простой >2 лет,
site:=0 при RD≥20; и только потом аддитивный балл (консенсус порогов: RD≥20, возраст≥10 лет,
ключи 10–100+, нет анкор-прогонов). Все правила — данные в чистом модуле + тесты.

**Дешёвые бесплатные сигналы на обогащение v2** (по возрастанию возни):
favicon 404 как маркер «выжженного» домена; gap-301/спам-паттерны из того же Wayback CDX
(нулевые допрасходы); Common Crawl domain ranks (бесплатный PR-подобный ранг, ~120M доменов);
ads.txt → sellers.json — атрибуция владельца сети за $0 по мёртвым через Wayback.

**Грабли из RIP-листа, которые мы уже обходим или не должны наступить:** Moz DA/PA мертвы как
таргет отбора (и не planned); «доход с паркинга» — мусорный сигнал (AFD выключен 02.2026, Bodis
закрыт); Ahrefs DR free требует атрибуцию — у нас стоит в /api/dr, не убирать; Wayback-плотность
кумулятивна (парковки тоже 12/12 мес — слабый фильтр, смотреть состав); семплированные спам-тесты
дают 5–8% ложных на живых сайтах — только составом сигналов, не одиночным чеком.

Осознанно не берём: Majestic/Moz как отдельные каналы (дублируют Ahrefs, свой юнит-контур),
трафик-чекер на дропах (§7), Cloudflare Radar (лицензия CC BY-NC — коммерческому скринингу нельзя).
