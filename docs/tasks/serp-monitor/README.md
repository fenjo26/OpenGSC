# SERP Monitor — параллельная разработка

Ветка интеграции: **`feat/serp-monitor`** (создана от `main` 359c09a). Всё, что описано здесь,
вливается сначала в неё. Руслан тестирует её целиком и только потом вливает в `main`.

## Что строим

Модуль `/serp-monitor`. Проект = рынок (движок · страна · язык · устройство) + набор запросов.
По расписанию модуль снимает **топ-100 целиком** по каждому запросу, хранит каждый съём,
считает изменения **по доменам**, волатильность и «штормы», ведёт каталог доменов
(впервые замечен, возраст регистрации, DR) и показывает это на трёх вкладках:

- **Рынок** — таблица запросов: лидеры, изменения с позициями, волатильность, своя позиция.
  Клик по строке — история выдачи по запросу и сравнение двух любых съёмов.
- **Штормы** — медианная волатильность каждого прогона против собственного фона проекта,
  отметки апдейтов Google, какие запросы и домены трясло сильнее всего.
- **Домены** — кто сколько запросов держит, кто растёт/падает, кто новый, кто молодой
  (зарегистрирован < N месяцев назад), кто «отскочил».

Источник выдачи v1 — **A-Parser пользователя (`SE::Google`)**: платы за запрос нет,
глубина 100. Ветка `aparser` в `runSerp` до сих пор не написана (остаток issue #5) — её
пишет T1, и она же заодно включает A-Parser в Rank Tracker.

**Не входит в v1** (фаза 2, в конце `CONTRACT.md`): сетки (NS, подсети, шаблоны текстов),
мобильная выдача, Bing/Yandex, пакетный режим A-Parser (`addTask`), платные провайдеры
по расписанию, «отправить выдачу в генератор».

## Порядок работ

```
T0 (один, последовательно) ──► T1 T2 T3 T4 T5 T6 (параллельно) ──► R (ревью и сборка) ──► тест Руслана ──► main
```

1. **T0** делает фундамент и коммитит **прямо в `feat/serp-monitor`**. Пока T0 не закоммичен,
   остальные не стартуют: они ветвятся от его коммита.
2. **T1…T6** — каждый в своей ветке `feat/serpmon-tN` от `feat/serp-monitor`, в своём worktree.
3. **R** вливает ветки в `feat/serp-monitor` в порядке **T2 → T1 → T4 → T3 → T5 → T6**
   (сначала чистая логика, потом то, что на неё опирается).
4. Руслан тестирует по разделу «Как тестировать» ниже.
5. `feat/serp-monitor` → `main` одним merge-коммитом.

## Worktree — только из терминала Мака

Все сессии работают в одном клоне `~/Downloads/opengsc`, поэтому `git checkout -b` запрещён —
он выдернет ветку из-под соседей. Каждой задаче — свой worktree.

> **Не создавай worktree из песочницы Cowork/VM.** Git записывает в `.git/worktrees/<имя>/`
> абсолютный путь той машины, где выполнена команда. Из VM это `/sessions/…/mnt/opengsc`,
> которого на Маке нет, — worktree сломан для Руслана. Проверено 2026-09-15. Команды ниже
> выполняются в терминале Мака (или агентом, который работает прямо на Маке).

```bash
cd ~/Downloads/opengsc

# T0 — на самой ветке интеграции
git worktree add .worktrees/serpmon-t0 feat/serp-monitor

# T1…T6 — ТОЛЬКО после коммита T0
git worktree add .worktrees/serpmon-t1 -b feat/serpmon-t1 feat/serp-monitor
# …то же для t2…t6

# в каждом worktree:
ln -sfn ../../node_modules .worktrees/serpmon-tN/node_modules     # 1.7 ГБ, не копировать
cd .worktrees/serpmon-tN && npx prisma generate                    # свой клиент, схема уже с моделями T0
```

`src/generated` **не** симлинкать на основной клон: после T0 схема в worktree новее, и общий
клиент либо устареет, либо испортит `main`. `.worktrees/` не в `.gitignore` — `git add` только
свои файлы. Уборка после сборки: `git worktree remove .worktrees/serpmon-tN`.

Если агент работает там, где `prisma generate` невозможен (нет бинарника движка): гоняй узкий
`tsc` и докладывай ошибки по категориям — ожидаемы только `TS2339 Property 'serp…' does not
exist on type 'PrismaClient'` и каскад `TS7006` от них.

## Правила, которые нельзя нарушать

- **Локали — только T0.** `npm run check:i18n` требует одинаковые ключи в 7 файлах
  (`en ru uk fr es de zh`). Все ключи всех задач перечислены в `CONTRACT.md` §7, T0 создаёт их
  заранее. Понадобился новый ключ — используй его в коде и допиши в раздел «Дополнительные
  ключи» своего отчёта. В локали не добавляй.
- **Никаких миграций.** Проект деплоится через `prisma db push` (см. `docker-entrypoint.sh`),
  `prisma/migrations/` не используется. `prisma/schema.mysql.prisma` генерируется сам
  (`prisma.config.ts`) и в git не лежит — не редактировать.
- **Тесты регистрируются сами.** T0 дописывает в конец `test:unit` глоб
  `src/lib/serpmon/*.test.ts`. Любой `*.test.ts` в этой папке запускается без правки
  `package.json`. Тесты клади только туда.
- **Схема:** типа `Json` нет (SQLite) — JSON хранится в `String` с комментарием `// JSON: <shape>`.
  `createMany({ skipDuplicates })` на SQLite не работает — сначала читаем существующие ключи,
  потом делим на insert/update. Пачки не больше **400** параметров.
- **A-Parser:** никогда не парсить `resultString`, только `results[0]` (`rawResults: 1`). Пустой
  ответ без `totalcount = 0` — это ошибка прокси, а не «выдача пустая» (`parserResultProblem`).
  Id опций берутся из пресета живого инстанса, а не из документации.
- **Стоимость в UI** для A-Parser: «self-hosted · no per-request cost», никогда `$0.00`.
- **Доступ:** чтение — `workspaceUserId()` (право `read`). Создание, правка, удаление,
  «Проверить сейчас», обогащение — `workspaceUserId("act")`. A-Parser — свой сервер без оплаты
  за запрос, поэтому `act`, а не `spend`. Любой будущий платный провайдер — `spend`.
- **Линт:** новые файлы — 0 ошибок `eslint`. Два правила, которые бьют чаще всего:
  `react-hooks/set-state-in-effect` (не делай `useEffect(() => setX(…))`, корректируй state
  во время рендера) и `@typescript-eslint/no-explicit-any` (`prisma as any` — только с
  `eslint-disable-next-line` и причиной).
- **Next.js здесь не тот, что в обучении** (`AGENTS.md`): перед роутами и страницами прочитай
  нужный гайд в `node_modules/next/dist/docs/`. Параметры динамических роутов — смотри, как
  сделано в существующих `src/app/api/**/[id]/route.ts`, и повторяй.
- **Таблица без схемы — не 500.** Инстанс, который подтянул код, но не сделал `db push`, получает
  `{ notMigrated: true }`, а страница показывает «выполните `npx prisma db push`». Образец —
  `schemaMissing()` в `src/lib/drops/store.ts`.

## Как тестировать (для Руслана, после R)

**Только на копии базы.** После `db push` в базе появятся таблицы `Serp*`. Если потом запустить
`main` без модуля, `docker-entrypoint.sh` сделает `db push` без `--accept-data-loss` и, скорее
всего, откажется стартовать, потому что пришлось бы удалить таблицы. Поэтому тест — на копии.

```bash
cd ~/Downloads/opengsc/.worktrees/serpmon-t0          # worktree ветки интеграции
cp ../../.env .                                        # .env в git не лежит
cp ../../dev.db ./serpmon-test.db
DATABASE_URL="file:./serpmon-test.db" npx prisma db push
DATABASE_URL="file:./serpmon-test.db" npm run dev
```

Чеклист приёмки:

1. `npx tsx scripts/aparser-serp-probe.ts "casino online" ar es` — печатает id опций пресета
   `SE::Google`, число органических результатов (ожидается 90–100), первые три строки и
   `totalcount`. Если результатов ≤ 10 — не подхватилась глубина, дальше не идти.
2. Меню → «SERP Monitor». Без A-Parser — плашка со ссылкой в настройки, без ошибок.
3. Новый проект: Аргентина / es / глубина 100 / интервал «вручную», 20 запросов из CSV с группами.
4. «Проверить сейчас» — прогресс идёт, по окончании у каждого запроса статус `ok` или понятная
   причина. Вкладка «Рынок»: изменений ещё нет, лидеры есть.
5. Через час ещё раз «Проверить сейчас». Появились изменения: **один домен — одна плашка**,
   с позицией (`+host #34`, `−host было #57`, `↑ host 12→5`). Платформы (facebook, instagram,
   apps.apple.com…) скрыты переключателем.
6. Выключить прокси в A-Parser и снова «Проверить сейчас» → запросы `failed` с причиной
   `aparser_blocked_or_empty`, **и ни одной плашки «−» из-за этого**.
7. «Штормы»: до 7 прогонов — «калибровка», графика шторма нет. Чтобы проверить сам детектор,
   есть юнит-тесты T2; ждать 7 дней не нужно.
8. «Домены» → «Загрузить возраст»: у `.com`/`.com.ar` появляется дата регистрации; у зон без
   открытого RDAP/WHOIS — понятная причина, а не пусто.
9. Telegram: кнопка «Тестовое уведомление о шторме» в настройках проекта приходит.
10. `npm run check` зелёный. Страница нормально выглядит на телефоне.

Потом — merge в `main`, `npx prisma db push` на проде, перезапуск.
