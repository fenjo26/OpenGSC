# Automatic index checks (Google URL Inspection)

Вкладка сайта **Indexing → Automatic index checks** и планировщик `src/lib/indexing/` тратят
**бесплатную** квоту Google URL Inspection API вместо платных сервисов (XMLRiver и др.).
Кнопка «проверить выбранные URL» никуда не делась — теперь у неё есть автопилот.

## Как устроена квота

- **2 000 проверок в день на ресурс (property)** и 600 в минуту — лимиты Google.
- День сбрасывается **в полночь по Тихоокеанскому времени** (`America/Los_Angeles`). В Салониках
  это 10:00 летом и 11:00 зимой; в UTC — 07:00 летом (PDT, UTC−7) и 08:00 зимой (PST, UTC−8).
- Мы держим себя строже Google по минутам: не больше **60 проверок в минуту** (пауза ≥ 1 с),
  в 10 раз ниже лимита.
- Все три пути — автопроверка, ручная кнопка на вкладке Indexing, MCP-инструмент `inspect_url`
  — тратят **одну и ту же квоту**, поэтому пишут в один журнал `InspectionQuota`
  (`property` = `Site.siteId`, `day` = тихоокеанский день). Счётчик «Сегодня: used/2000»
  растёт от всех трёх.
- **Бюджет автопроверки** (0…1800, по умолчанию 1000) — доля дневной квоты, которую планировщик
  имеет право тратить сам. Ручные проверки бюджетом не ограничены: человек выбрал URL — их
  проверяем. Но когда Google уже ответил 429 за сегодня, ручной путь сразу говорит «квота
  исчерпана до полуночи PT» вместо сотни запросов, каждый из которых вернёт 429.
- Каждая ошибка квоты ставит в журнале `exhaustedAt`; до тихоокеанской полуночи все пути
  молча прекращают попытки.

## Очередь приоритетов

Планировщик тикает каждые 10 минут и для каждого сайта с включённой автопроверкой берёт порцию
`ceil(остаток бюджета / оставшиеся до полуночи PT 10-минутные слоты)`, но не больше 100 за тик —
квота размазывается по суткам, и выпавшая страница находится в течение дня, а не через сутки.
Сайты одного владельца обходятся по кругу (round-robin), чтобы один сайт на 5 000 URL не съедал
каждый тик. Порядок URL:

1. **new** — ни разу не проверялись; свежие (`firstSeenAt`) первыми.
2. **changed** — инвентарь увидел `added/changed/restored`, а последняя проверка старше этого
   изменения.
3. **not_indexed** — пора перепроверить (`googleNextCheck` настал), прошлый статус «не в
   индексе» (по умолчанию каждые 3 дня).
4. **stale_indexed** — пора перепроверить, прошлый статус «в индексе» (по умолчанию каждые
   14 дней).

URL со статусом инвентаря ≠ `active` (пропавшие из sitemap) не проверяются. К каждому сроку
перепроверки добавляется детерминированный джиттер ±10 % по хешу URL — тысяча URL, проверенных
в один день, не возвращается в очередь тоже разом в один день. Ошибка API откладывает
перепроверку на сутки.

## Что пишет проверка

В `SitemapUrl`: `googleStatus` (= coverageState ?? verdict), `googleCoverage`, `googleReason`,
`googleChecked`, `googleVerdict`, `googleLastCrawl`, `googleCanonical` (только если отличается
от самого URL), `googleNextCheck`. В `PageInspection` — последний статус (его читает вкладка).
В `PageInspectionHistory` — строка **только при смене статуса** (одна на URL в сутки, день UTC):
это лента «когда страница вошла/вышла», из неё же считается алерт о выпадении.

## Алерт о выпадении

URL сменил статус «в индексе» → «не в индексе», и у него есть клики за последние 28 дней
(`DailyMetric`, `searchType = "web"`) → одно сообщение в сутки на сайт: шаблоны
`indexLossTitle` / `indexLossMsg` (язык — из настроек алертов), до 10 строк
«URL — причина — клики», дальше «и ещё N». Дедупликация через `AlertEvent`
(`type: "index_loss"`, `dedupeKey: index_loss:<siteId>:<UTC-день>`), доставка `notifyUser`
с событием `index` (Telegram/Slack; после волны October — любой подключённый канал с
включённым событием «Индексация»).

## Покрытие по дням

Раз в сутки (первый тик после 00:00 UTC) планировщик пишет `IndexCoverageDaily` из активных
URL: сколько в индексе / не в индексе / неизвестно и причины не-индексации. На панели —
стек-график за 90 дней.

## Почему «в индексе» определяется по строкам

API отдаёт `verdict` (PASS/NEUTRAL/…) и `coverageState` («Submitted and indexed»,
«Crawled - currently not indexed», …). Таблица соответствия — `isIndexedCoverage` в
`src/lib/indexing/queue.ts`: `PASS` и две «проиндексированные» строки → да; список
«непроиндексированных» строк («Duplicate…» — по префиксу) → нет; **всё остальное → «не знаю»**,
не ноль и не догадка. Непроверенные URL считаются «неизвестно», а не «не в индексе».

## Когда платные проверчики всё ещё нужны

- **Сайта нет в Search Console.** URL Inspection работает только с подтверждённым ресурсом и
  только от аккаунта с доступом. Чужие сайты — по-прежнему XMLRiver/нейросеть в X-ray.
- **Больше 2 000 URL в день на один ресурс.** Квоту нельзя купить; большой сайт будет
  проверяться несколько дней (очередь это переживает — приоритеты и сроки перепроверки
  сохраняются).
- **Нужна скорость проверки конкретных URL вне очереди** — ручная кнопка/`inspect_url` тратят
  ту же квоту, так что и здесь платный сервис останется платным, а бесплатный — не быстрее.

## Честное ограничение

URL Inspection **сообщает, что знает Google, но не запрашивает индексацию**. Проверка не
ускоряет попадание страницы в индекс. Для отправки на индексацию остаются IndexNow
(Bing/Yandex), 2index и NeuralIndexer. «Проверить» и «отправить» — разные действия, и вкладка
Indexing держит их раздельно.

## Настройка

Сайт → вкладка Indexing → карточка «Automatic index checks»: переключатель, дневной бюджет
(0…1800), интервалы перепроверки (проиндексированные / непроиндексированные, в днях),
алерт о выпадении. Кнопка «Check a batch now» гоняет ту же очередь вручную (лимит 200 за раз,
тратит квоту, расход пишется в `auto`). MCP: `get_index_coverage` — статус очереди, квоты,
покрытия и выпадений; `inspect_url` — живая проверка до 10 URL.

Таблиц нет (`InspectionQuota`/`IndexCoverageDaily` и новые колонки `SitemapUrl`) → панель
просит выполнить `npx prisma db push`, планировщик отключается до рестарта. Никаких миграций —
деплой как всегда через `prisma db push`.
